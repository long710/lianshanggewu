Section 01: 架构深度解析

核心大脑：业务中台 (Off-Chain)

Storage Layer

PostgreSQL 主/从

系统的中心存储层，负责保存所有结构化数据，包括事件元数据、用户画像、高频订单记录等。主从架构确保了极高的数据可用性。

Transmission Layer

Relayer (中继器)

核心枢纽：连接链下与链上。

当后台创建事件时，Relayer 会监听数据库变化，并将指令发送至链上 event-pod，完成合约实体的创建。

Processing Layer

gRPC Server & Worker

gRPC Server: 接收来自 event-rs 的高性能情报流。
Worker: 后台任务处理器，执行数据清洗、状态同步与定时任务。

API 矩阵

Admin/Operator API 管理 B 端后台与项目配置。
Frontend API 为 C 端用户提供实时查询服务。

Real-time Sync

Websocket: 向前端推送实时赔率变化、K 线图更新，确保毫秒级的交互体验。

Section 01: 架构深度解析

资产锚点：链上合约层 (On-Chain)

模块化隔离设计

架构明确指出“每个 B 端用户都有一套这么一套合约”，实现了彻底的物理隔离与资产确权。

Event-Pod

管理单个预测事件的生命周期：创建、开启、暂停、结束。由中台 Relayer 触发创建。

Funding-Pod

专门的资金池合约。用户投注资金 直接进入 合约，非托管设计确保资金不经过数据库。

ChooseMe Oracle 合约

系统的“终极裁判”。接收预言机提交的 Truth 数据，并触发事件的最终结算。

情报引擎 (event-rs)

这是系统的“情报触角”。基于高性能服务，监听现实世界（体育比分、币价 API）并通过 gRPC 同步至中台。

任务 01: 动态事件情报引擎

Section 03: x402 技术解决方案

唤醒沉睡代码：x402 支付协议

HTTP 402 原生支付

402 状态码在 1999 年被预留用于“未来的数字支付系统”，ChooseMe 让其在 Web3 时代真正落地。

投币式逻辑 直接调用 API -> 服务器返回支付要求 -> 钱包转账 -> 拿到数据。
零门槛 无需注册、无需订阅，用多少付多少。

Verification Parameters

amount
10 Tokens
destination
0x1ec105...
nonce
x402_k7m2n9

Code Implementation (Nonce in Calldata)

const baseData = tokenContract.interface.encodeFunctionData("transfer", [destination, payAmount]);
const nonceHex = ethers.hexlify(ethers.toUtf8Bytes(nonce));
const txData = ethers.concat([baseData, nonceHex]); //

// ERC-20 忽略多余字节，但记录永久保存于链上备查

为什么 Nonce 重要？ 防止重放攻击。每个 Nonce 只能对应一笔交易，确保一笔付款不能被多次冒用。

Section 03: x402 技术解决方案

六步闭环：x402 交互流程设计

01
白嫖请求

客户端不带认证直接发起 GET 请求。

02
返回 402

服务端返回支付额、地址与唯一 Nonce。

03
链上支付

构造交易，将 Nonce 塞入 Data 字段上链。

04
提交证明

带上交易哈希与 Nonce 重新发起请求。

05
链上验证

服务端去链上核查 Nonce 与到账状态。

06
JWT 收据

返回数据并颁发 1 小时有效的 JWT 收据。

Core Innovation Points

• HTTP 402 成为 Web 原生支付能力 • Nonce 嵌入 Calldata 实现高效防重放 • 去中心化、链上可验证数据源 • JWT 收据优化重复支付体验
Section 04: 链上订单簿技术解决方案

高频需求 vs 性能限制：CLOB 的挑战

预测市场特性

长尾效应 事件数量极多，单事件流动性可能极度有限。
性能矛盾 高频交易需求与通用公链性能限制之间的天然冲突。

混合限价订单簿 (Hybrid CLOB)

目前主流（Polymarket）采用的方案，追求极致交易体验。

链下撮合 (Off-chain) 挂单、撤单、撮合在高性能服务器进行，通过 EIP-712 签名授权。
链上结算 (On-chain) 撮合成功后 Operator 打包上链，验证签名并执行资产转移。

全链上订单簿 (Fully On-Chain)

极致去中心化，依托高性能公链（Solana, Sui）。

内存撮合引擎 链上维护红黑树或 Crit-bit 树，直接在区块生成过程中撮合。
抗审查性 只要区块链运行，市场永不关闭，无中心化审核风险。
Section 04: 链上订单簿技术解决方案

核心工具：条件代币框架 (CTF)

CTF (Conditional Tokens Framework)

基于 Gnosis 开发的 ERC-1155 标准。支持将核心资产（如 USDC）拆分成互斥的条件代币（YES / NO）。

Logic Detail

"合并流动性：Sell YES = Buy NO。架构自动将 Sell YES 订单映射为 Buy NO。"

Efficiency formula
1 YES + 1 NO = 1 Unit

该恒定公式极大地提高了资本效率，确保了“原子交换”的确定性。
